# Nudge Phase 3 — Electron Tray — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A **clickable** OS notification and a persistent tray icon, so you are caught even when VS Code is closed and you are in a browser — and clicking takes you straight to the waiting window.

**Architecture:** An Electron app that is a *client* of the Phase 1 engine over the same socket. **No engine changes.** It reuses the client pattern already proven in the VS Code extension.

**Tech Stack:** Electron, TypeScript, esbuild (same bundling approach Phase 2 needed), `electron-builder` for signed artefacts.

## Why this exists when Phase 2 already ships a UI

Stated plainly, because it determines what this must get right:

- **macOS `osascript` notifications cannot carry a click action.** That is the Phase 1 limitation Phase 2 was meant to work around, and it only worked around it *inside the editor*. Electron's `Notification` supports a real `click` handler. **This is the reason Phase 3 exists.**
- **A VS Code toast is invisible when VS Code is closed or you are in Chrome** — which is the original problem the whole product was built for. The tray is the outer ring.
- **It is editor-agnostic** — it also serves people running Claude Code in a plain terminal.

What Phase 3 does **not** replace: the extension reports `frontmost` to the engine, which stops it nagging about a window you are already looking at. Nothing outside the editor can know that. The two are complementary; ship both.

## Global Constraints

- **No engine changes.** If a task appears to need one, stop and report it. The socket API (`subscribe`, `list`, `snooze`, `mute`, `resolve`, `idle`, `frontmost`) is fixed.
- **`@nudge/shared` is the single source of the wire format.** Do not re-declare protocol types. Phase 2's `packages/vscode/src/client.ts` is the reference implementation for reconnect-with-backoff — **extract and share it rather than copying it**, or the two will drift.
- **Must bundle.** Phase 2 shipped a `.vsix` that died on activation with `ERR_MODULE_NOT_FOUND` because `@nudge/shared` resolves through a monorepo symlink that does not exist in a packaged artefact. 84 passing tests could not catch it. **Every packaging task must prove the artefact loads, not merely that it builds.**
- **A leak per restart is unacceptable** — this runs at login, for weeks.
- **The tray must not become a second brain.** No tier logic, no escalation timing, no suppression rules. It renders engine state and sends commands.
- **Errors log via `console.error('nudge tray: …', err)`** — the convention used throughout Phases 1 and 2.
- **Do not ship an app that silently does nothing.** If the engine is unreachable, the tray must say so and offer to start it.

## Task 1: Extract the shared engine client

**Files:**
- Create: `packages/client/**` (new package `@nudge/client`)
- Modify: `packages/vscode/src/client.ts` → re-export from the shared package
- Test: move `packages/vscode/test/client.test.ts` to the new package

The VS Code extension and the tray both need connect/subscribe/reconnect-with-backoff. Phase 2's implementation is already reviewed and proven (backoff resets after a successful reconnect; the decoder resets so a partial NDJSON frame cannot bleed across reconnects; `dispose()` cancels both socket and timer). **Copying it would guarantee drift** — the `TIER_TEXT` duplication between the engine and the extension is already an open finding of exactly this kind.

- [ ] **Step 1:** Create `@nudge/client` with `EngineClient` moved verbatim, plus its tests.
- [ ] **Step 2:** Point `packages/vscode` at it; the extension's own tests must still pass unchanged.
- [ ] **Step 3:** Rebuild and repackage the `.vsix`; **verify it still loads** with the standalone stubbed-`vscode` check from Phase 2 — this refactor is exactly the kind that breaks bundling silently.
- [ ] **Step 4:** Full suite green, `tsc --build` clean, commit.

## Task 4: Clickable notifications — the reason this phase exists

**Files:** `src/notify.ts`, `test/notify.test.ts`

- [ ] **Step 1:** Electron `new Notification({title, body})` with a real `click` handler calling `focusSession`.
- [ ] **Step 2:** **De-duplicate per session**, exactly as Phase 2's `Toaster` does — the engine broadcasts on every state change and a notification per broadcast is unusable. Clear on resolve so a later re-block notifies again.
- [ ] **Step 3:** Desktop notifications carry **full detail** (the actual question, the exact command) — that asymmetry against the phone payload is deliberate and documented: it never leaves the machine.
- [ ] **Step 4:** **This replaces Phase 1's `osascript` path when the tray is running.** Decide and document how: either the tray tells the engine to suppress its own desktop notifier, or the engine keeps firing and the user gets two. **Two notifications for one event is a real defect** — pick one and test it. Note that suppressing the engine's notifier may need an engine change, which is out of scope; if so, prefer having the tray *not* duplicate what the engine already shows, and say so.
- [ ] **Step 5:** Prove the click handler fires and calls focus — with a deliberate break showing the test goes red.
- [ ] **Step 6:** Commit.

## Task 5: Focus from outside the editor

**Files:** `src/focus.ts`, `test/focus.test.ts`

The tray has no editor API, so it works from the surface fingerprint the hook recorded at session start (`kind`, `termProgram`, `tty`, `wtSession`, `app`).

| Surface | Mechanism |
|---|---|
| VS Code / Cursor / Windsurf | `code <cwd>` / `cursor <cwd>` — focuses the existing window holding that folder |
| Claude desktop app | Focus by bundle id (the `app` field the Phase 1 amendment added) |
| Terminal.app / iTerm2 | AppleScript targeting the recorded tty |
| Windows Terminal | Focus by process + `WT_SESSION` |
| Linux | `wmctrl`/`xdotool` if present — **X11 only, Wayland is a known gap** |

- [ ] **Step 1:** Implement per surface with an injected spawner, as Phase 1's `desktop.ts` did.
- [ ] **Step 2:** **Escape every interpolated value per platform.** Phase 1 shipped a PowerShell injection because one escaping function written for AppleScript was reused for PowerShell — where `\"` ends the string rather than escaping it. Use separate, clearly-named escapers and test each with a payload containing quotes, `$(...)` and `;`.
- [ ] **Step 3:** Unknown surface → copy the project path to the clipboard and say so in a notification. Honest beats magical.
- [ ] **Step 4:** **Focusing must not resolve the wait** — same rule as Phase 2. Give this module no `send` capability at all, which is how Phase 2 made it structurally impossible.
- [ ] **Step 5:** Commit.

## Open questions to settle before or during Task 4

1. **Double notification.** With both the engine's `osascript` notifier and the tray running, one event may produce two banners. Task 4 Step 4 must resolve this.
2. **Do the tray and the extension conflict?** Both connect and subscribe; both may act on the same session. Subscribing twice is harmless, but two `frontmost` reporters would fight — the extension should remain the only one sending `frontmost`.
3. **Distribution.** Unsigned macOS apps are quarantined by Gatekeeper. Signing needs an Apple Developer account; without one, document the right-click-open workaround honestly rather than pretending it installs cleanly.
